# Build, Test and Simulate

How to run everything in this repo without hardware. The design is in `docs/ARCHITECTURE.md` (v0.2); this page covers the code. Simulation results are in `docs/SIM-REPORT.md`.

## Layout

| Path | What |
|---|---|
| `src/tidesvc/` | The service (ARCHITECTURE 6-7): `codec`, `ingest`, `derive`, `calibration`, `noaa`, `energy`, `alerts` + `notify`, `tempest`, `api`, `export`, `db`, `core` (wires it all to `handle(event)` / `tick(now)`), `service` (asyncio + uvicorn), `radio` (meshcore adapter, unverified), `cli` |
| `src/sim/` | Simulator. Separate package; it imports `tidesvc`, never the reverse (a test enforces this) |
| `firmware/` | PlatformIO project for the Heltec V3. `lib/tidecore/` is the portable core (codec, burst stats, battery state machine, cold rule, CE pulse, one-cycle orchestration); `src/main.cpp` and `include/hal_heltec_v3.h` are stubs |
| `tests/vectors/` | Golden vectors shared by pytest and the C++ host tests (`packets_v1.json`, `stats_v1.json`, `fw_logic_v1.json`), generated by `tools/gen_vectors.py` |
| `tests/unit/`, `tests/sim/` | pytest suites; `tests/fixtures/` holds one recorded NOAA 8531942 hilo response |

## Python environment

Python 3.12. The normal path (needs network for PyPI):

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e '.[dev,sim]'          # add ,plots for PNGs; ,radio on the mini PC only
```

`requirements.txt` lists the exact versions this build was tested with. **Not verified here:** a clean install from PyPI (the session had no network access by rule). This machine's build used an offline venv over the Anaconda 3.12 site-packages instead:

```bash
python3.12 -m venv --system-site-packages .venv
PYTHONNOUSERSITE=1 .venv/bin/pip install -e . --no-deps --no-build-isolation
export PYTHONNOUSERSITE=1    # keeps ~/.local's numpy 2.5 out (it breaks matplotlib/scipy there)
```

`.venv/` and `sim-out/` are git-ignored.

## Tests

```bash
.venv/bin/python -m pytest -q                    # everything, offline (~1 min)
.venv/bin/python -m pytest -q -m "not slow"      # skips the 30-day and deficit simulations (~15 s)
make -C firmware/test/host                       # C++ host tests on the shared vectors
cmake -S firmware/test/host -B /tmp/tc && cmake --build /tmp/tc && (cd /tmp/tc && ctest)   # same via CMake
ruff check src tests tools                       # lint
.venv/bin/python tools/gen_vectors.py --check    # vectors up to date
```

Results at the time of writing: **pytest 349 passed** (0 failed, 0 skipped; 347 with `-m "not slow"`), including the C++ build-and-run wrapper; **C++ host tests 449 checks passed** (Apple clang 16, `-Wall -Wextra -Werror -pedantic`, also clean under UBSan; AddressSanitizer would not initialise on this macOS host, so it is unverified); ruff clean.

## Simulator

```bash
.venv/bin/python -m sim.run                                  # default 30-day December + 21-day shaded deficit -> docs/SIM-REPORT.md
.venv/bin/python -m sim.run --sweep 5 --tie-sensitivity 14   # what produced the committed report (~7 min)
.venv/bin/python -m sim.run --scenario quick --report /tmp/r.md --no-plots
```

Exit status is non-zero if any required acceptance check fails. Databases and PNG plots go to `sim-out/` (not committed). Scenarios live in `src/sim/scenario.py`; the acceptance checks in `src/sim/acceptance.py`.

What is simulated: harmonic tide with surge and weather noise; ramp/float with foot traffic and boat wakes; an SCL3300-like sensor (offset, temperature drift, noise, quantization); the node running the firmware rules (`sim.fwlogic`, held to the same vectors as the C++); December insolation on a vertical south face, a 1 W panel, the BQ25185 (VINDPM, /CE, NTC backstop, 6 h timer, DONE) and a LiFePO4 cell; a lossy MeshCore link with relayed and direct duplicates, corruption, a repeater outage and a gateway unplug with a 16-frame companion queue; a fake NOAA provider (astronomical extremes; Sandy Hook residual). All of it feeds the real `tidesvc.core.Core`, and `/api/v1/level/current` is probed through the real FastAPI app.

## Running the service

```bash
cp src/tidesvc/config.example.toml config.toml   # edit; secrets go in .env, never in config.toml
python -m tidesvc --config config.toml --env .env serve      # API on :8120
python -m tidesvc --config config.toml cal add-obs --kind level_check --angle -9.8 --at 2026-12-05T12:47Z
python -m tidesvc --config config.toml cal add-obs --kind tape --freeboard 2.143 --at 2026-12-05T13:17Z
python -m tidesvc --config config.toml cal add-obs --kind tape --freeboard 0.992 --at 2026-12-05T19:31Z
python -m tidesvc --config config.toml cal fit-install
python -m tidesvc --config config.toml cal datum-tie --from 2026-12-05 --to 2026-12-19
python -m tidesvc --config config.toml cal show | approve <id> | reject <id>
python -m tidesvc --config config.toml reprocess --from 2026-12-05T00:00Z
```

`.env` keys: `TIDE_CHANNEL_SECRET`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `ALERT_EMAIL_TO`, `TEMPEST_TOKEN`. Without SMTP settings the service still runs and alerts stay visible at `/api/v1/alerts`. Docker/compose, the udev rule and `deploy.sh` (ARCHITECTURE 8) are not built yet.

## Decisions and deviations from ARCHITECTURE v0.2

Implemented as the architecture says unless listed here. Items marked **(Nick)** need a decision.

1. **Energy verdict (Nick).** Charger-accepted harvest is capped once the cell is full, so harvest/consumption tends to 1.0 for any node whose cell keeps reaching full; the 2.0/1.0 thresholds alone can never say `surplus` for a healthy node (the simulation got `marginal` for a 1 W panel that refilled the cell on 10 of 13 days). Implemented: full on at least half of the qualifying days means `surplus`; otherwise the ratio thresholds. `energy_ratio_is_lower_bound` is reported. (ARCHITECTURE 6.6 already calls full-charge days the "panel is large enough" signal.)
2. **Harvest definition (Nick, bench B10).** The `ipanel` sample is taken while the node is awake. When the panel is not the limit (charging off, or CV taper near full), it measures the node's ~25 mA awake current, not harvest; the literal integral overstated harvest by about 17x in the December run and turned the deficit run into `marginal`. Implemented per sample: VINDPM (vpanel < vbat + 1.0 V) counts ipanel; charging but not panel-limited counts ipanel - `i_read_ma` + modelled average load; not charging counts at most the modelled load. New config: `energy.i_read_ma` (25 mA placeholder, bench value replaces it), `energy.vindpm_margin_mv`.
3. **DONE at night (Nick, firmware).** With no panel input the BQ25185 STAT pins float to 1/1, so ARCHITECTURE 4.7's "DONE = STAT 1/1 while /CE is LOW" fires every night. The firmware rule also requires vpanel >= 3.0 V; the server ignores DONE without panel voltage.
4. **Cold-inhibit hours.** Counted only with panel input present ("too cold to charge", not "night"); ARCHITECTURE 6.6 says "time with cold_charge_inhibit set".
5. **Calibrated envelope.** ARCHITECTURE 6.4's +/-0.5 deg margin is about 6.6 cm of level, so a real surge above the calibrated range would be thrown away as out of range. The install fit sets the envelope from the tape levels -1.0 m / +2.0 m (`calibration.ENVELOPE_*`).
6. **Residual lag.** `residual = level_smooth - pred` mixes a ~12.5 min-lagged median with an unlagged prediction (about 5 cm error at mid-tide). The prediction gets the same trailing median over the same reading times (`derived.predicted_smooth_m`); `predicted_m` is still the plain prediction at t. Excess rise uses the same pair.
7. **Before the datum tie (Nick).** Until calm-day extremes tie h0 to MLLW (end of the 14-day shakedown), level is reported relative to the bulkhead mark and `residual_m` is null with `DATUM_NOT_TIED`, so surge alerts cannot fire during the shakedown. The architecture does not say what should happen in that window.
8. **"2 consecutive evaluations"** for the surge rules means two consecutive new readings (the engine ticks every 60 s but the residual changes every 5 min).
9. **Spec gaps decided (proposals, Nick):** monthly refit needs >= 12 matched calm-day extremes including both H and L; a datum tie needs >= 4 (TEST-PLAN SV-C7). Even-count median = mean of the two middle values, SD = population SD (FW-U4), one rule in `stats_v1.json` for firmware and server. Calm day = Sandy Hook residual below 0.10 m for the whole local day with at least half the 6-min samples present. Firmware `high_sd` flag at > 0.25 deg (same as the server's validity limit). A hardware cold fault is inferred from STAT 0/1 below +5 C die temperature.
10. **Storage.** Timestamps are UTC epoch seconds (REAL) rather than text; the API renders ISO-8601 Z. Additive columns: readings `rx_at`, `path_len`, `snr_db`; derived `t`, `live`, `predicted_smooth_m`, `smooth_reason`, `residual_reason`; calibrations pitch envelope and `datum`; a `component_state` table for gateway/NOAA/Tempest status. De-duplication looks back 24 h.
11. **`projected_days_to_empty`** needs a DONE anchor for the state of charge; before the first DONE it is null (so the projection half of `LOW_BATTERY` cannot fire until then).
12. **Paths.** Firmware is in `firmware/` (ARCHITECTURE 4.8 says `src/node-firmware/`) and the shared vectors are in `tests/vectors/` (ARCHITECTURE 10, TEST-PLAN 2 and DEV-PLAN E3.4 say `tests/fixtures/packets_v1.json`), as instructed for this build.

## Contradictions found between the planning docs

- PRD FR3 says the install procedure fits "theta0 and effective L"; ARCHITECTURE 6.5 / ADR-009 fixes theta0 and fits h0 and L_eff. Followed the architecture.
- PRD FR4 says node silent after 15 min; ARCHITECTURE 6.8 alerts at 30 min while the API goes stale at 15 (DEV-PLAN 7 item 1, still open). Followed the architecture; both are config values.
- TEST-PLAN SV-N4 expects `RAPID_RISE` to fire on "+0.35 m over 3 h", but that is 0.117 m/h, below the 0.15 m/h threshold, so it cannot. The unit test uses +0.35 m over 1 h.
- ARCHITECTURE 4.7 (DONE rule) and 6.6 (harvest integral, verdict thresholds, cold hours) conflict with the BQ25185 behaviour described in BATTERY.md 4.1 (STAT open-drain, VINDPM); see deviations 1-4.

## Not verified

- `tidesvc.radio` (meshcore_py adapter): never run against meshcore_py 2.3.15 or a companion; event payload names are assumptions (spike S1 / E5.3).
- Live NOAA: one hilo read of 8531942 was recorded as a fixture and parses; the Sandy Hook observed/6-min client has not touched the live API. SMTP sending and the Tempest HTTP client have not been run against real servers.
- Firmware board build (`pio run -e heltec_v3_tide`): not built (framework and MeshCore would be fetched from the network); HAL and uplink are stubs. The `native` PlatformIO env is declared but the tests run through the Makefile/CMake.
- Clean `pip install` from PyPI, Docker image, deploy scripts.
- Every simulated physical constant (panel, charger, cell, wakes, sensor) is a model, not a bench measurement.
